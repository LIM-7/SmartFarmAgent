## 1. 背景与目标

### 1.1 项目现状

SmartFarmAgent 已按「感知 → 决策 → 执行」闭环完成总体设计（见 TechDoc）：

- 边缘端：ESP32 / ESP32-CAM 单芯片，数据采集、拍照、本地规则、microSD 日志
- 平台：Node.js + Express + MQTT.js + WebSocket，MySQL / SQLite
- 前端：Vue 3 + ECharts
- 视觉：Python + OpenCV + YOLOv8（独立服务，Node.js 编排）
- 智能体：大模型（OpenAI 兼容接口）+ RAG 知识库

### 1.2 本方案目标

用户赴江苏叁拾叁智慧农业有限公司考察后，提出按如下完整业务闭环细化设计：

```
数据采集 → 环境 / 虫情 / 苗情监测 → 评估意见 → 施肥方案 → 决策执行 → 反馈
```

UI 以**网页（手机优先）**为主，本方案在 TechDoc 架构基础上补全「四情监测、评估意见、施肥/灌溉处方、执行反馈」四个业务环节的详细设计。

### 1.3 借鉴来源

江苏叁拾叁智慧农业有限公司（官网 www.33iot.com）：

- 四情监测体系（墒情 / 虫情 / 苗情 / 灾情），多源感知统一入平台
- 「感知-分析-决策-执行」闭环（无人农场、草莓园等案例）
- 「一田一策」处方图、变量施肥、按需水肥
- 执行结果回写，数据全留痕，支撑模型迭代

## 2. 总体架构

沿用 TechDoc 六层架构，本方案重点细化智能决策层与数据层：

```
┌─ 展示层 ──────────────────────────────────────────────┐
│ Vue 3 + ECharts + WebSocket：大屏看板 / 手机端四页     │
└────────────────────────┬──────────────────────────────┘
┌─ 智能决策层 ───────────┼──────────────────────────────┐
│ 评估规则引擎 │ 处方生成器 │ 智能体编排（大模型+RAG）    │
│ 输出：评估意见 / 施肥灌溉方案 / JSON 指令（白名单）    │
└────────────────────────┬──────────────────────────────┘
┌─ 云端平台层 ───────────┼──────────────────────────────┐
│ Node.js + Express：REST API / MQTT 网关 / WebSocket    │
└────────────────────────┬──────────────────────────────┘
┌─ 通信层 ───────────────┼──────────────────────────────┐
│ MQTT（设备上行下行）/ HTTP（图片）/ WebSocket（前端）  │
└────────────────────────┬──────────────────────────────┘
┌─ 边缘层 ───────────────┼──────────────────────────────┐
│ ESP32 / ESP32-CAM：采集 / 拍照 / 本地规则 / microSD    │
└────────────────────────┬──────────────────────────────┘
┌─ 感知执行层 ───────────┴──────────────────────────────┐
│ 传感器组（BH1750/DHT11/土壤/可选气象）│ 摄像头         │
│ 执行器：继电器 / 水泵 / 电磁阀 / 风扇 / 补光 / 水肥    │
└───────────────────────────────────────────────────────┘
```

### 2.1 数据流

**上行**

```
ESP32 采集环境数据 → MQTT 主题上报（JSON）→ Node.js 订阅 → MySQL
ESP32-CAM 定时拍照 → HTTP 上传 → 视觉服务识别 → 虫情/苗情表
```

**下行**

```
Web UI 确认方案 → 智能决策层生成指令
  → 白名单校验 → MQTT 下发 → ESP32 本地复核 → 执行器动作
  → 执行状态回传 → control_log / prescription 回写 → 反馈闭环
```

## 3. 感知与四情监测设计

### 3.1 环境监测（墒情 + 小气象）

| 数据 | 传感器 | 接口 | 采集周期建议 |
| --- | --- | --- | --- |
| 温度 / 湿度 | DHT11 | 单总线 | 60s |
| 光照 | BH1750 | I2C（开漏需上拉） | 60s |
| 土壤湿度 | 土壤湿度模块 | ADC | 300s |
| 雨量 / 风速（可选） | 气象传感器 | I2C/脉冲 | 300s |

统一 JSON 上报结构，字段名固定：

```json
{ "device_id": "esp32-01", "ts": "2026-08-29T10:00:00+08:00",
  "temp": 26.3, "humi": 62.1, "light": 150, "soil": 45 }
```

### 3.2 虫情监测

- ESP32-CAM 定时拍照（可配置 30/60min），夜间 LED 补光
- 视觉服务 YOLOv8 识别害虫类别并计数，输出置信度
- 结果写 `pest_log`：类型 / 数量 / 图片 / 置信度 / 告警标记
- 阈值：单次计数超阈值 → 评估层触发防治建议

### 3.3 苗情监测

- 定时拍照 + 表型分析：绿度指数（颜色统计）、叶面积/株高估算（目标检测）
- 可选多光谱简化方案：红/近红外双通道估算 NDVI（低成本）
- 结果写 `crop_growth_log`：绿度 / 叶面积 / 株高 / 生长阶段
- 趋势判断：绿度连续下降 → 评估层提示养分/水分胁迫

### 3.4 灾情（预留）

接入气象预警（雨量、风速、极端温度），触发告警进入评估层，本期可不实现。

## 4. 评估意见设计

评估层输出结构化意见，写 `evaluation_log`：

```json
{ "type": "ENV|PEST|CROP", "level": "NORMAL|WARNING|ALARM",
  "summary": "土壤偏干且连续 3 次低于阈值",
  "advice": "建议执行灌溉方案（水量 500ml）",
  "snapshot": { "soil": 18, "temp": 28, "humi": 55 } }
```

### 4.1 规则引擎（v1，先落地）

| 规则 | 条件 | 等级 | 意见/建议 |
| --- | --- | --- | --- |
| 温度偏高 | T > 32℃ 且连续 3 次 | ALARM | 开启风扇/通风 |
| 湿度偏高 | H > 80% | WARNING | 除湿 |
| 光照不足 | L < 50 lx | WARNING | 补光 |
| 土壤偏干 | S < 25% | ALARM | 灌溉 |
| 闷热复合 | T > 30℃ 且 H > 75% | WARNING | 通风防病 |
| 虫情 | 单次计数 > 阈值 | WARNING | 针对性防治 |
| 苗情 | 绿度连续 3 次下降 | ALARM | 检查养分/水分 |

规则以 JSON 配置存储，平台可改、本地 ESP32 可同步阈值子集（断网自持）。

### 4.2 大模型评估（v2，演进）

智能体聚合传感器最新值、视觉结果、历史趋势，结合 RAG 知识库生成诊断意见并附依据；模型不可用时降级到规则引擎（TechDoc 容错设计）。

## 5. 施肥 / 灌溉方案设计

### 5.1 方案结构（prescription）

| 字段 | 说明 |
| --- | --- |
| crop_type / growth_stage | 作物与生长阶段 |
| plan_type | FERT / IRRIGATE / PEST |
| params | JSON：水量、N-P-K 比例、执行时长、目标设备 |
| status | DRAFT → CONFIRMED → EXECUTING → DONE / FAILED / EXPIRED |

### 5.2 方案生成

- **v1 查表模型**：作物 × 阶段 → 需水量/需肥量，再按墒情/光照修正系数
- **v2 智能体处方**：大模型 + RAG 知识（种植手册/测土配方）生成「一田一策」处方，含推理依据
- 默认**人工确认**后才执行，可配置自动执行（仅限低风险动作）

### 5.3 执行设备映射

| 方案类型 | 执行设备 | 执行参数 |
| --- | --- | --- |
| IRRIGATE | 水泵 / 电磁阀 | 时长、流量 |
| FERT | 水泵 + 施肥罐 / 蠕动泵 | 水量、肥液比例 |
| PEST | 喷雾泵（预留） | 时长、浓度 |
| ENV | 风扇 / 除湿 / 补光 | 开关、PWM 档位 |

## 6. 决策执行与反馈闭环

1. 方案生成 → 人工确认（或自动）
2. 智能决策层输出 JSON 指令：`{action, params, session_id}`
3. 白名单校验（动作 + 参数边界）+ 本地规则复核（冲突以本地安全为准）
4. MQTT 下行 → ESP32 执行 → 状态回传（带 session_id 确认）
5. 后端写 `control_log` + 更新 `prescription.exec_result` + 记 `decision_log`
6. 执行结果进入下次评估输入，形成持续闭环

## 7. 数据存储设计

### 7.1 MySQL 业务表（farm_monitor v2）

保留：`sensor_data`、`control_log`、`alarm_log`、`device_status`

新增：

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| pest_log | 虫情记录 | device_id / sample_time / pest_type / count / image_path / confidence / alarm_flag |
| crop_growth_log | 苗情记录 | device_id / sample_time / green_index / leaf_area / height / growth_stage / image_path |
| evaluation_log | 评估意见 | device_id / eval_time / type / level / summary / advice / snapshot(JSON) |
| prescription | 施肥灌溉方案 | device_id / crop_type / growth_stage / plan_type / params(JSON) / status / exec_result |
| decision_log | 决策审计 | presc_id / input_ref(JSON) / rule_version / output(JSON) / executed_at / feedback |

### 7.2 其他存储

- 时序数据：`sensor_data`（或 SQLite 时序备份）
- 图片与识别结果：文件目录 + 路径入库
- 知识库向量索引：RAGFlow / Dify（智能体方案演进用）

| --- | --- |

## 12. 风险与注意事项

- BH1750 开漏输出需外部上拉；DHT11 时序敏感，读取间隔不宜过密
- ESP32 本地规则优先于云端指令，冲突以安全为准（TechDoc 已约定）
- 时间统一：ESP32 NTP、MySQL NOW()、前端 UTC+8
- 接口鉴权与指令白名单必须前置；局域网演示可加简单 token
- 摄像头夜间需补光 LED；图片存储定期清理
- 设备离线判断：`device_status.last_seen` 超阈值提示
- 公开仓库注意隐私脱敏：文档与代码不出现个人信息与内部规划
